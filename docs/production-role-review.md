# 角色与生产化评估

## 当前结论

当前系统是可运行的 Phase 1 原型：三角色登录、课程归属、选课、作业提交和实时课堂基础链路已经存在，但还不适合直接作为学校生产系统。主要差距是对象级授权、身份生命周期、业务闭环和运维安全，而不是角色数量不足。

## 现有角色边界

- `student`：只能看到已选课程，可提交作业和加入实时课堂。
- `teacher`：管理自己授课的课程、作业、提交和课件 Agent。
- `admin`：目前是全局角色，管理 API 尚不完整，且部分代操作会错误地把管理员写成教师归属。

前端侧栏过滤仅用于体验，后端授权才是安全边界；所有新功能都应同时增加路由守卫、API policy 和越权测试。

## 分阶段路线

### 阶段 0：安全止血

修复管理员代教师操作的归属与审计；集中实现 `can_view_course`、`can_manage_course`、`can_grade_assignment`、`can_manage_users` policy；补齐 401/403/404 越权测试；上线前启用 refresh/CSRF 防护、登录限流、上传限制、审计和关闭演示账户。

### 阶段 1：单校分层权限

保留单校/学院部署边界，引入 `organization_id`、院系、学期、课程班级和 membership。角色逐步扩展为 `platform_admin`、`school_admin`、`academic_admin`、`teacher`、`teaching_assistant`、`student`、`observer`，并为角色授予范围和有效期。

### 阶段 2：教学闭环

完成学生作业提交历史、教师批改/rubric/重交、公告、资料、讨论、考勤、成绩册、通知、录播和课程级 RAG 权限继承。

### 阶段 3：生产平台

接入学校 SSO/SCIM/MFA；对象存储、队列、监控、备份恢复、灾备、CI/CD、漏洞扫描、隐私与数据保留；补齐 E2E、负载、权限模糊测试和渗透测试。

## 首次学校上线门槛

至少完成阶段 0，且课程/作业/成绩/通知四条核心链路通过角色矩阵和端到端测试；管理员操作必须有明确 scope、审计记录和可追溯的实际授课教师归属。
